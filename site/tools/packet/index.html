Encapsulation: envelopes inside envelopes

A packet on the wire is a set of nested envelopes. Ethernet says which machine on this cable; IP says which host on the internet; TCP/UDP say which program on that host; the payload is the actual conversation. Each layer prepends its own header and treats everything inside as opaque cargo: 

┌──────────────────────────────────────────────────────────┐
│ Ethernet   dst MAC · src MAC · type            (14 bytes) │
│ ┌──────────────────────────────────────────────────────┐  │
│ │ IPv4      src IP · dst IP · TTL · proto     (20 bytes)│  │
│ │ ┌──────────────────────────────────────────────────┐ │  │
│ │ │ TCP     ports · seq/ack · flags · window (20+ B) │ │  │
│ │ │ ┌──────────────────────────────────────────────┐ │ │  │
│ │ │ │ payload   HTTP, TLS, DNS, …                  │ │ │  │
│ │ │ └──────────────────────────────────────────────┘ │ │  │
│ │ └──────────────────────────────────────────────────┘ │  │
│ └──────────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────────┘

Things the decoder checks for you

  • IPv4 header checksum — recomputed at every hop (the TTL changes), covers the header only.
  • TCP/UDP checksums — computed over a pseudo-header that borrows the IP addresses, so a packet delivered to the wrong host fails validation. Captures of outgoing traffic often show "invalid" here because the NIC fills the checksum in hardware after the capture point (checksum offload).
  • TTL fingerprints — initial TTL is typically 64 (Linux/macOS), 128 (Windows) or 255 (routers). A TTL of 57 usually means "Linux box, 7 hops away".
  • DNS compression pointers — names in responses reuse earlier bytes via 0xC0xx back-references; the decoder follows them like a resolver would.
  • SNI in plain text — the hostname inside a TLS ClientHello is not encrypted. Decode the sample and find it.

Where to get real bytes

Drop a .pcap or .pcapng file straight onto this page. Or copy a single frame — Wireshark: right-click a packet → Copy → …as a Hex Dump; tcpdump: tcpdump -XX -c 1 port 53.

The pcap file format, briefly

A classic .pcap file is beautifully simple: a 24-byte global header (magic A1 B2 C3 D4 — its byte order tells you the writer's endianness — plus version, snaplen and link type), then each frame as a 16-byte record header (timestamp seconds + microseconds, captured length, original length) followed by the raw bytes. The newer .pcapng is a block container: a Section Header Block (magic 0A 0D 0D 0A), Interface Description Blocks (one per capture interface, each with its own link type and clock resolution), and an Enhanced Packet Block per frame with 64-bit timestamps. This page reads both, including captures from loopback (NULL), raw-IP tunnels and Linux -i any cooked captures (SLL), whose pseudo-headers are stripped before decoding.

Frequently asked questions

Can I open a .pcap file online without Wireshark?

Yes — drop a .pcap or .pcapng file onto this page. You get a clickable frame list with timestamps and per-frame summaries, and each frame decodes layer by layer with verified checksums. Parsing happens entirely in your browser, which matters for captures: they routinely contain credentials, cookies and internal hostnames, so they should never be uploaded to a random website.

What hex dump formats can I paste?

Raw hex strings, xxd output, hexdump -C output, Wireshark's Copy … as a Hex Dump, and C-style \x escapes. Offsets and ASCII gutters are stripped automatically.

Which protocols does the decoder understand?

Ethernet II with VLAN tags, ARP, IPv4, IPv6, TCP including options, UDP, ICMP and ICMPv6, DNS with name-compression pointers, TLS ClientHello (including SNI and ALPN), HTTP and NTP.

Does it verify checksums?

Yes — IPv4 header, TCP, UDP and ICMP checksums are recomputed and compared, including the pseudo-header that TCP and UDP borrow from the IP layer. Captures of outgoing traffic often show invalid checksums because the NIC fills them in after the capture point (checksum offload).

My dump doesn't start with an Ethernet header — can I still decode it?

Yes. The decoder auto-detects the first layer, and you can override it with the first layer selector to start at IPv4, IPv6, TCP, UDP, ARP, a DNS message or a TLS record — useful for captures taken above layer 2, like tcpdump on a tunnel interface.

Is it safe to paste production packet captures?

Parsing happens entirely in your browser; the bytes are never transmitted. Only the optional Share button uploads content, and those links expire after 30 days.
