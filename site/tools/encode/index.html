Why Base64 exists (and why it's 4/3 bigger)

        

          Old transport channels (email!) only promised to deliver 7-bit ASCII safely. Base64 re-expresses arbitrary
          bytes using 64 safe characters: every 3 bytes (24 bits) become 4 characters of 6
          bits each — hence exactly 33% growth, and = padding when input length isn't a multiple
          of 3. The URL-safe variant swaps +/ for -_ because + means "space" in
          query strings and / is a path separator. JWTs use the URL-safe flavor without padding.
        


        
Percent-encoding has two modes

        

          encodeURIComponent escapes everything that could confuse a URL (?, &,
          =, /…) — use it for individual parameter values. encodeURI keeps URL
          structure characters intact — only for already-assembled URLs. The classic bug is using the wrong one:
          a=1&b=2 as a value must become a%3D1%26b%3D2.
          The +-means-space rule is a separate convention from HTML forms
          (application/x-www-form-urlencoded), not part of percent-encoding itself.

          ASCII is valid UTF-8 unchanged — the design trick (by Thompson & Pike, sketched on a placemat in 1992)
          that let UTF-8 conquer the world. The continuation-byte prefix 10… means you can seek into the
          middle of a file and resynchronize.
        


        
A JWT is signed, not secret

        

          header.payload.signature, each part base64url. The payload is readable by anyone —
          decoding it (what this tool does) requires no key. The signature only proves who issued it and that it
          wasn't modified. Never put secrets in claims; always validate exp, aud and
          iss server-side; and reject "alg": "none".
