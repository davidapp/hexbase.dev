How many bits is a character worth?

Entropy is counted in bits, and each character of a random string contributes log₂(alphabet size) of them. That single fact explains every "standard" key length you've ever copy-pasted:

AlphabetBits per charChars for 128 bitsChars for 256 bits
binary (01)1128256
decimal (0–9)≈ 3.323978
hex (0–9 a–f)exactly 43264
base6462243

Hex is the sweet spot for keys: exactly 4 bits per character, case-insensitive, safe in URLs, configs and shell commands. That's why a 128-bit key is "32 hex chars" and a 256-bit key is "64 hex chars" — the sizes aren't arbitrary, they're AES-128 and AES-256 written out.

Why 128 and 256 bits specifically

128 bits is where brute force stops being an engineering problem and becomes a physics problem — sweeping 2¹²⁸ keys at a trillion guesses per second takes about 10¹⁹ years, a billion times the age of the universe. 256 bits isn't there because 128 is weak; it buys margin against the unknown (Grover's algorithm on a future quantum computer would halve the effective strength to a still-comfortable 128) and matches the output size of SHA-256, which is why HMAC-SHA-256 secrets should carry 256 bits per RFC 2104.

Math.random() is not a key generator

Math.random() is built for speed, not secrecy: V8 runs xorshift128+, whose entire internal state can be recovered from a few consecutive outputs — after that, every "random" value it will ever produce is predictable. crypto.getRandomValues() instead drains the operating system's CSPRNG (getrandom(2) on Linux, BCryptGenRandom on Windows), which is continuously reseeded from hardware noise and designed so that observing outputs tells you nothing about the next one. This page only ever calls the latter.

The modulo-bias trap

The classic bug in hand-rolled generators: take a random byte, compute byte % 10, call it a digit. But 256 doesn't divide by 10 — the digits 0–5 each arrive from 26 byte values while 6–9 get only 25, a 4% skew that compounds across a long key and fails randomness audits. The fix is rejection sampling: throw away bytes ≥ 250 and roll again, so every digit is exactly equally likely. This tool does that for decimal; binary and hex divide 256 evenly, so nothing needs rejecting. 

byte:   0..249  → keep, digit = byte % 10   (25 bytes per digit — fair)
byte: 250..255  → reject, draw a new byte    (~2.3% of draws)

Frequently asked questions

Is it safe to generate secret keys in a browser?

For most uses, yes: this page draws from crypto.getRandomValues, the browser's cryptographically secure generator, fed by the operating system's entropy source. Generation happens entirely locally — the string is never transmitted, which you can verify in the network tab. For regulated or high-assurance environments, generate keys inside an HSM or your platform's key-management service instead.

How long should an API key or secret be?

128 bits of entropy — 32 hex characters — is the accepted floor for anything that must resist brute force. HMAC-SHA-256 secrets should carry 256 bits (64 hex characters), matching the hash output size per RFC 2104 and RFC 7518. Beyond that, extra length adds nothing unless a specification demands it.

Why are keys usually 32 or 64 hex characters long?

A hex character carries exactly 4 bits, so 32 characters hold 128 bits and 64 characters hold 256 bits — the two standard symmetric key sizes (AES-128, AES-256, HMAC-SHA-256). The lengths look arbitrary in a config file, but they're just those key sizes written out in hex.

Can I use Math.random() to generate keys?

No. Math.random() is a fast statistical generator, not a cryptographic one: its internal state can be recovered from a handful of outputs, after which every past and future value is predictable. Use crypto.getRandomValues in JavaScript, secrets in Python, or SecureRandom in Java.
